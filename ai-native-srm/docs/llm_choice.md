# Архитектура LLM-слоя и выбор провайдера (Шаг 2, уточнено на Шаге 6)

## 1. Короткий ответ

В прототипе работают пять провайдеров за одним интерфейсом (`core/llm/base.py`):

| Провайдер | Когда используется |
|---|---|
| `api` | любая модель с OpenAI-совместимым API (OpenRouter, DeepSeek, Groq, Qwen, OpenAI, свой шлюз): три переменные — и она отвечает первой |
| `mock` (по умолчанию без ключей) | демо, тесты, работа без сети и без ключей — автотесты идут на нём |
| `gigachat` | кандидат для пилота, когда модель обязана быть в РФ: 152-ФЗ, function calling, русский язык |
| `yandex` | второй «российский» кандидат: дешевле на Lite/Pro, зрелый API Yandex Cloud |
| `local` | бесплатный контур на своих весах (GigaChat-20B-A3B, YandexGPT-5-Lite): данные не покидают машину |

Переключатель — одна переменная (`LLM_PROVIDER`), код и тесты от выбора не зависят. Поэтому
«какой вендор» — вопрос `.env`, а не архитектуры: сравнить кандидатов можно на одном и том же
движке, не меняя код.

## 2. Почему LLM не является «мозгом» системы

Ключевое архитектурное решение: **модель не принимает решений**. Категория обращения, маршрут,
размер скидки, срок гарантии, SLA менеджера и все числа считаются кодом (`core/decision.py`,
`core/tools.py`, `core/policy.py`); LLM отвечает за две вещи: разобрать запрос в структуру
(`understanding`) и переписать готовые факты в вежливый ответ (`generation`).

Что это даёт при выборе провайдера:

* «выдумал цену/скидку» невозможно структурно — числа LLM проходят белый список `guardrails`, а
  в спорных категориях текст вообще детерминированный (`core/templates.py`, TTFR < 100 мс);
* смена провайдера — это смена формулировок, а не поведения: политика, решения и метрики не меняются;
* деградация модели (таймаут, отказ, мусорный JSON) не ломает диалог: `FallbackChain` уходит к
  следующему провайдеру, затем к `mock`, а при полном отказе клиент получает честный шаблон
  (`templates.generic_fallback`) — Устав, Ст. 9 «клиент не остаётся в тишине».

## 3. Сравнение кандидатов (по публичным данным на конец 2026 года)

| Критерий | GigaChat | YandexGPT | DeepSeek / Qwen (self-hosted) | GPT/Claude |
|---|---|---|---|---|
| Русский язык | нативный, сильный на деловых текстах | нативный | хороший, но требует проверки на деловом тоне | хороший |
| Соответствие 152-ФЗ | да (Сбер) | да (Yandex Cloud, УЗ-3) | да, если self-hosted в своём контуре | нет без отдельного контура |
| Цена, ₽ / 1k токенов | Lite ≈ 0,065; Pro ≈ 0,5; Max ≈ 0,65 | Lite ≈ 0,2; Pro ≈ 0,4–1,2 | ≈ 0,01–0,05 (свои GPU, но CAPEX) | 3–5 ₽ и выше |
| Function calling / JSON | есть (Pro/Max), формат как у OpenAI | есть (5 Pro) | есть | есть, лучший |
| Контекст | до 128k | 32k (Pro 5.x) | 32k–1M | 128k+ |
| Оплата | рубли, пакеты токенов | рубли | свои серверы | иностранная карта/контракт |
| Риск санкций/доступа | низкий | низкий | низкий | высокий |

Вывод: **GigaChat** — выбор по умолчанию для российского заказчика (единый контур Сбера,
function calling, привычный формат API), **YandexGPT** — дешёвая альтернатива и второй шанс
в `FallbackChain`, **self-hosted** — запасной вариант при росте нагрузки и наличии GPU.

Цены у российских провайдеров меняются (у YandexGPT в 2026-м стоимость Pro снижали втрое),
поэтому таблица — ориентир для расчётов, а не оферта: финальную цифру даёт замер на своём трафике.

## 4. Что архитектура даёт на практике

```
LLM_PROVIDER=mock      → демо и тесты: ноль сети, воспроизводимо (260 passed)
LLM_PROVIDER=gigachat  → прод: GIGACHAT_CREDENTIALS, форматы как у OpenAI
LLM_PROVIDER=yandex    → прод: YANDEX_API_KEY + YANDEX_FOLDER_ID
```

* Единый интерфейс: `complete_json` (структура, temperature 0) и `complete_text` (формулировка).
* Таймаут задаётся в цепочке, а не внутри SDK: `FallbackChain` держит **общий** бюджет времени
  (2,5 с на понимание, 3,5 с на генерацию — из таймера Устава).
* Полный отказ всех провайдеров → шаблонный ответ + событие `pipeline_error`; в тестах этот путь
  проверен (`test_engine.py`).
* Провайдер не видит ПДн лишний раз: тексты проходят `core/privacy.py` перед логом/событием.

## 5. Что НЕ делалось и что делать перед пилотом

Честно: **реального замера провайдеров на нашем трафике не было** — нужны ключи и бюджет.
План замера (полдня работы, сценарий уже готов — бот и API принимают любого провайдера):

1. Взять 20–30 диалогов демо-набора + 20 стресс-кейсов (инъекции, спор, гарантия, лимит скидки).
2. Прогнать `LLM_PROVIDER=gigachat` и `yandex`, снять `GET /api/metrics`.
3. Сравнить: p95 TTFR по категориям, доля fallback-шаблонов, доля ответов, отклонённых guardrails,
   override_rate, субъективная оценка тона (5-балльная шкала, 2 оценщика).
4. Добавить в события `provider=<name>` (сейчас фиксируется `latency_ms`, но не движок) — тогда
   сравнение будет видно из метрик, а не из логов вручную.
5. Посчитать стоимость на 1 000 диалогов и на месяц; сверить с бюджетом.

Ожидаемый порядок: 1 диалог ≈ 2–4 обращения к модели ≈ 1–2k токенов; 10 000 диалогов/мес ≈
15–20 млн токенов ≈ **7,5–10 тыс. ₽/мес на GigaChat Pro** или ≈ 1–4 тыс. ₽/мес на Lite/YandexGPT Lite.
Цифра мала на фоне стоимости рабочего часа менеджера — но это оценка «по прайсу», проверять замером.

## 6. Промпты и их место в коде

| Промпт | Файл | Ответственность |
|---|---|---|
| Системный | `core/prompts/system.py` | Устав: иерархия истин, запреты, тон |
| Понимание | `core/prompts/understanding.py` | JSON со строгой схемой (`core/schemas.py`) |
| Генерация | `core/prompts/generation.py` | текст клиенту, temperature 0, факты в отдельном блоке |

Два принципа, которые снижают риск инъекций и галлюцинаций:

1. **Данные отделены от инструкций.** Факты из tools подаются в отдельном блоке и помечаются как
   данные, а не как продолжение инструкции — попытка «инструкций внутри данных» ловится
   pre-classifier'ом (`core/perception.py`) и `guardrails.detect_injection` (включая гомоглифы и base64).
2. **Формулировки, критичные для Устава** (сроки, remedy, отказ по скидке) берутся из шаблонов,
   а не из модели: модель может быть недоступна, а срок связи менеджера клиент обязан услышать.
