# Telegram-бот-анкета: заявка → карточка клиента

Отдельный бот от клиентского чата (`channels/telegram_bot.py`). Здесь нет ИИ и переписки:
бот задаёт пять вопросов, собирает данные о человеке и отправляет их в CRM. На сервере из
анкеты создаётся **карточка клиента**, поэтому данные сразу используются в работе сайта:
клиент виден в разделе клиентов, менеджер получает уведомление, а клиентский чат-бот находит
этого человека по `telegram_id`, когда он пишет в общий чат.

```
Telegram ──(анкета)──▶ channels/telegram_lead_bot.py ──POST /api/leads──▶ core/leads.py
                                                                              │
                                        клиент (карточка) + уведомление LEAD + событие lead_received
```

---

## Запуск

```bash
python -m channels.telegram_lead_bot --check   # настройки + доступность API, к Telegram не идём
python -m channels.telegram_lead_bot           # приём заявок (long polling)
```

Переменные окружения (см. `.env.example`):

| Переменная | Зачем |
|---|---|
| `TG_LEAD_BOT_TOKEN` | токен бота от [@BotFather](https://t.me/BotFather) — **отдельный** от клиентского бота |
| `BOT_API_TOKEN` | сервисный токен для `/api/leads` — тот же, что в `.env` бэкенда |
| `API_URL` | адрес API (по умолчанию `http://localhost:8000`) |
| `TG_MANAGER_CHAT_ID` | куда слать копию заявки менеджеру (можно несколько id через запятую) |
| `UI_URL` | адрес дашборда — попадёт ссылкой в уведомление менеджеру |

Токен бота **не** выдаётся наружу и не логируется; если `BOT_API_TOKEN` пуст, бэкенд отвечает
`503` — это сознательно, чтобы заявки не текли в CRM без защиты (Ст. 4).

## Что спрашивает бот

| Шаг | Вопрос | Обязательный |
|---|---|---|
| 1 | Как вас зовут? | да |
| 2 | Как называется ваша компания? | нет («-» — частное лицо) |
| 3 | Телефон для связи? | нет, но приводится к формату `+79991234567` |
| 4 | E-mail для документов? | нет |
| 5 | Что нужно? Коротко опишите задачу. | нет |

Правила диалога:

* пропуск — «-», «нет», «пропустить»; на обязательном вопросе пропуск отклоняется с пояснением;
* телефон не распознан → шаг повторяется, прогресс не сдвигается («Телефон не распознан. Пример: …»);
* `телефон/почта не указаны` → контактом становится сам Telegram: менеджер ответит в чате,
  заявка при этом не теряется;
* `/cancel` или «отмена» — выход; `/start` на любом шаге — анкета заново;
* перед отправкой показывается карточка «Проверьте, всё верно?» и кнопки-слова «да» / «заново»;
* API недоступен → клиент видит «Попробуйте ещё раз: «да»», ответы остаются в сессии и не теряются.

Персональные данные не нужны боту в логах: в события CRM уходит только длина запроса и факт
наличия контакта, полный текст — в карточке клиента (`core/leads.py`).

## Что происходит на сервере

`POST /api/leads` (заголовок `X-Bot-Token`) → `core/leads.py:apply_lead()`:

1. нормализация: телефон «8 (999) 123-45-67» → `+79991234567`, обрезка пробелов, проверка имени;
2. поиск существующего клиента по `telegram_id` → телефону → e-mail (первое совпадение);
3. нет клиента — создаётся карточка (`source="telegram_lead_bot"`); есть — заполняются только
   пустые поля, изменившиеся фиксируются по событию;
4. уведомление менеджеру (`type="LEAD"`) и событие `lead_received` (без ПДн в payload);
5. ответ `{ok, client_id, created, changed, name, company, notification}`.

`GET /api/leads?limit=20` — последние заявки списком (для дашборда и отладки), тоже по токену.

## Тесты

```bash
pytest tests/test_lead_bot.py -q     # 23 теста: анкета, пропуски, ошибки, конфиг, HTTP-вызов
pytest tests/test_leads.py -q        # серверная часть: нормализация и карточка клиента
```

Логика опроса вынесена в `channels/lead_flow.py` без aiogram — поэтому проверяется обычными
тестами, а обвязка бота остаётся тонкой. `aiogram` нужен только для реального запуска
(`pip install -r requirements.txt`), в остальных случаях тесты работают без него.
