# Telegram-бот: меню, профиль, обращения, чат с ИИ, вызов менеджера

Бот — единственный канал, где клиент общается с компанией (на сайте клиентской части нет:
там работает менеджер). Внутри бота восемь разделов: профиль, обращения, новое обращение,
чат с ИИ, вызов менеджера, помощь с базой знаний, каталог и настройки. Всё, что клиент
делает в боте, попадает в CRM: карточка клиента, диалог с ИИ-пайплайном, уведомления
менеджеру и его ответы в дашборде.

```
Telegram ──меню/текст──▶ channels/telegram_lead_bot.py ──/api/bot/*──▶ app/routers/bot_api.py
                              │  ▲                                          │
                     mock_telegram.py (офлайн-прогон)                core/*: ai_engine, leads, handoff
                              │  ▼                                          │
                    channels/bot_flow.py + bot_ui.py  ◀── экраны     карточка клиента, диалог, уведомления
```

Раньше каналов было два: бот-анкета (собирал заявку) и клиентский чат-бот (пересылал текст
в пайплайн) — клиент путался, какой из двух с ним говорит. Теперь это один бот: анкета стала
разделом «Профиль», а переписка с ИИ — разделом «Чат с ИИ».

## Меню

Нижний **виджет-меню** (постоянная клавиатура Telegram) — восемь разделов:

| Кнопка | Что делает |
|---|---|
| `🆕 Обращение` | новое обращение: тема → описание → уходит в пайплайн, отвечает ИИ |
| `📁 Мои обращения` | список обращений со статусами (🤖 ведёт ИИ, ⏳ ждёт менеджера, 🧑‍💼 ведёт менеджер, ✅ закрыто) |
| `👤 Профиль` | карточка клиента в CRM: имя, компания, телефон, e-mail, сколько обращений; правка по полям |
| `🤖 Чат с ИИ` | свободный диалог: наличие, цены, скидки, доставка, гарантия |
| `💬 Менеджер` | позвать человека: обращение уходит в HOLD, менеджер получает саммари |
| `❓ Помощь` | что умеет бот, список команд, частые вопросы из базы знаний |
| `🖥 Каталог и цены` | витрина справочника CRM: 6 разделов, 17 категорий, 122 позиции с ценами и наличием |
| `⚙️ Настройки` | уведомления об ответах менеджера и технические детали ответов ИИ |

### Каталог в боте

`🖥 Каталог и цены` группирует справочник CRM в **шесть разделов**: техника (`💻`),
серверы и комплектующие (`🧩`), сеть (`🌐`), печать (`🖨`), расходники и офис (`📦`),
ПО и услуги (`💿`). Внутри раздела — страницы по **6 позиций** (`CATALOG_PAGE`), листалка
`◀`/`▶` правит то же сообщение, в первой строке видно «Страница N из M».

Источник — тот же `data/catalog.json`, по которому отвечает ИИ (`core.tools.catalog_items`),
поэтому цена в витрине и в ответе ассистента всегда совпадают. Разделы и категории
заданы в `channels/bot_ui.py` (`CATALOG_GROUPS`, `CATALOG_GROUP_TITLES`); категория,
не попавшая ни в один раздел, показывается в «Прочее» — ничего не теряется.
Услуги (монтаж, настройка, утилизация) идут без числа на складе: наличие у них не «0 шт.»,
а «срок согласуем при заказе».

Тот же список продублирован **кнопкой «Меню»** рядом с полем ввода: при запуске бот публикует
команды (`setMyCommands`) — `/profile`, `/appeals`, `/chat`, `/manager`, `/id`, `/cancel` — и
короткое описание (`setMyShortDescription`). Клавиатуру Telegram показывает после команды,
поэтому в диагностике и при старте бот подсказывает: **если разделов не видно — отправьте `/start`**.

**Навигация правит сообщение.** Нажатие inline-кнопки не создаёт новое сообщение, а заменяет
экран в том же (в терминале это помечено «↻»). Обычный текст и команды приходят новыми
сообщениями — так же ведёт себя бот в Telegram.
Каждый экран дополнительно показывает **inline-кнопки** (они правят то же сообщение, поэтому
навигация не засоряет чат): открыть обращение, ответить в нём, позвать менеджера, закрыть
обращение, перейти по разделам базы знаний, спросить ИИ про конкретную модель.

Команды: `/start` `/menu` `/profile` `/appeals` `/chat` `/manager` `/help` `/id` `/cancel`.

### Состояния диалога

| Состояние | Что ждёт бот |
|---|---|
| `MENU` | нажатие кнопки или вопрос: любой текст уходит в чат с ИИ |
| `PROFILE_FILL` | анкета профиля (`channels/lead_flow.py`): имя обязательно, остальное — «-» |
| `PROFILE_FIELD` | правка одного поля: «-» очищает значение, остальные поля сохраняются |
| `APPEAL_TEXT` | описание обращения после выбора темы |
| `CHAT` | продолжение переписки в том же обращении |

## Обращения и статусы

Обращение — это диалог в CRM (`conversations`), а не отдельная сущность: спасибо этому
менеджер видит ту же переписку, что и клиент, и может ответить прямо из дашборда.

```
клиент пишет ─▶ /api/bot/messages ─▶ ai_engine.process_message (канал telegram)
                                        │
                      ИИ отвечает ──────┴──── эскалация (спор, нет данных, просьба клиента)
                                                        │
                                            HOLD + уведомление менеджеру
                                                        │
                            менеджер отвечает в дашборде ─▶ messages + outbox
                                                        │
                    бот забирает ответы (/api/bot/me/inbox) и отправляет клиенту в Telegram
```

Статусы клиент видит человеческими словами: «в работе, отвечает ИИ», «ждёт менеджера»,
«ведёт менеджер», «закрыто». Кнопка «✅ Закрыть» закрывает обращение (resolve) — история
остаётся в CRM.

## Запуск

```bash
python -m channels.telegram_lead_bot --check          # настройки, бот в Telegram, webhook, API, LLM
python -m channels.telegram_lead_bot                  # long polling: диалог + доставка ответов
python -m channels.telegram_lead_bot --drop-webhook   # снять webhook и очистить старые апдейты
python -m channels.telegram_lead_bot --mock           # тот же диалог в терминале, без Telegram
```

`--check` показывает, какой это бот в Telegram (`@username`) и ссылку `t.me/<username>`, список
команд и разделов виджета, предупреждает про webhook и печатает, какой LLM-провайдер отвечает
(в демо — `mock`, ключи не нужны). Перед стартом бот
сам проверяет, не занят ли токен другим экземпляром: при конфликте он не уходит в бесконечные
повторы, а печатает готовые команды для Windows.

Переменные окружения (см. `.env.example`):

| Переменная | Зачем |
|---|---|
| `TG_LEAD_BOT_TOKEN` | токен бота от [@BotFather](https://t.me/BotFather) (обязателен) |
| `BOT_API_TOKEN` | сервисный токен для `/api/bot/*` и `/api/leads` — тот же, что в `.env` бэкенда |
| `API_URL` | адрес API (по умолчанию `http://localhost:8000`, в Docker — `http://api:8000`) |
| `TG_MANAGER_CHAT_ID` | куда дублировать уведомления менеджеру (можно несколько id через запятую) |
| `UI_URL` | адрес дашборда — попадёт ссылкой в уведомление |

Токен не логируется. Если `BOT_API_TOKEN` пуст, бэкенд отвечает `503` — это сознательно,
чтобы обращения не текли в CRM без защиты (Ст. 4).

## Mock-режим: весь диалог без токенов, сети и модели

Отдельный вход для демонстрации и отладки — `channels/mock_telegram.py`. Он запускает **ту же**
логику бота (`bot_flow` + `bot_ui`), но транспорт — терминал, а CRM — в памяти
(`channels/mock_crm.py`): карточка клиента, обращения, ответы mock-ИИ, ответы менеджера.

```bash
python -m channels.mock_telegram            # интерактивный диалог в терминале
python -m channels.mock_telegram --demo     # автопрогон по всем экранам (для показа и отчёта)
python -m channels.mock_telegram --api http://localhost:8030 --bot-token <BOT_API_TOKEN>
                                            # тот же диалог, но против живой CRM и её пайплайна
```

В диалоге: номер кнопки или её подпись; `→nav:help` — «нажать» кнопку по callback data;
`менеджер <текст>` — ответить клиенту как менеджер из дашборда (проверка доставки);
`фид` — что сейчас видит менеджер; `доставка` — забрать ответы менеджера.

Mock-ИИ не выдумывает числа: он берёт их из тех же источников, что боевой пайплайн —
Policy Matrix (`data/policy_seed.json`: скидки, срок ответа менеджера, замена по гарантии),
каталог (`data/catalog.json`) и базу знаний (`data/knowledge_base.md`, тот же поиск, что в RAG).
Если факта нет — mock честно уходит в HOLD и зовёт менеджера.

Разговор он ведёт по-человечески (`channels/mock_crm.py`): обращается к клиенту по имени из
карточки, здоровается, отвечает на «спасибо» и «ты бот?», подбирает технику по разделу и
бюджету («нужен ноутбук для бухгалтерии до 80 000» → три варианта из каталога), сравнивает
две модели, считает скидку по тирам политики. Подбор включается только когда вопрос
действительно про подбор: иначе фраза «гравировка на корпусе принтера» не превращается в
подбор комплектующих, а уходит менеджеру. Такие же живые формулировки — в шаблонах
(`core/templates.py`) и промптах генерации (`core/prompts/generation.py`), через которые
отвечает боевой пайплайн.

Пример из `--demo` (сокращённо):

```
👤 клиент> Нужно 10 МФУ PX-M4200, какой будет итог со скидкой?
🤖 10 × 38 900 ₽ = 389 000 ₽. На сумму от 150 000 ₽ политика даёт 12% → итого 342 320 ₽.
   Счёт и договор оформляет менеджер — передать ему заявку?
👤 клиент> Здравствуйте! Одно из МФУ пришло с трещиной на корпусе, нужна замена.
🤖 Сочувствую ситуации — так быть не должно. Передал обращение менеджеру: по регламенту он
   отвечает в течение часа. Обычно вопрос решается так: замена, скидка, бонус — согласуем с вами.
📤 в CRM (лента менеджера): ⏳ HOLD · обращение #1001: … → саммари готово, ждёт менеджера
```

## Как это устроено в коде

| Модуль | Ответственность |
|---|---|
| `channels/bot_ui.py` | экраны: тексты и кнопки (виджет-меню, inline-навигация). Без aiogram и сети |
| `channels/bot_flow.py` | логика диалога: состояния, команды, нажатия, вызовы сервиса через протокол `BotService` |
| `channels/telegram_lead_bot.py` | транспорт Telegram: aiogram-обвязка, клавиатуры, доставка ответов, уведомления менеджеру, `--check` |
| `channels/mock_crm.py` | mock-CRM: профиль, обращения, ответы mock-ИИ, очередь доставки — в памяти |
| `channels/mock_telegram.py` | офлайн-транспорт: рисует экраны в терминале, поддерживает автопрогон |
| `channels/manager_feed.py` | формат уведомлений менеджеру в Telegram (типы DISPUTE/SECURITY/… ) |
| `app/routers/bot_api.py` | фасад `/api/bot/*`: профиль, обращения, переписка, доставка, вызов менеджера |

Правило канала не нарушено: в боте нет бизнес-логики — он рисует экраны и пересылает данные.
Решения принимает пайплайн (`core/`), а доступ к нему закрыт сервисным токеном.

## Ручки фасада `/api/bot/*`

Все — с заголовком `X-Bot-Token`; владелец обращения сверяется по `telegram_id`, поэтому
чужой диалог через бота не открыть.

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/bot/me` | карточка клиента по `telegram_id` (`found=false`, если его ещё нет) |
| POST | `/api/bot/me` | сохранить профиль; заводит карточку и уведомляет менеджера (`LEAD`) |
| GET | `/api/bot/me/appeals` | мои обращения: статус, тема, последнее сообщение, счётчики |
| GET | `/api/bot/me/appeals/{id}` | переписка по обращению (`?after=` — для поллинга) |
| POST | `/api/bot/me/appeals/{id}/manager` | позвать менеджера: HOLD, саммари, уведомление `HANDOFF_REQUEST` |
| POST | `/api/bot/me/appeals/{id}/close` | клиент закрыл обращение (resolve) |
| POST | `/api/bot/messages` | сообщение клиента в пайплайн (как `POST /api/messages`, но с проверкой владельца) |
| POST | `/api/bot/me/inbox` | забрать недоставленные ответы ИИ и менеджера (доставка «at-least-once») |

## Запуск как сервис (чтобы бот работал постоянно)

Long polling не требует белого IP и вебхука — боту достаточно исходящего соединения.

**Docker** (рекомендуемый способ, если API уже в compose):

```bash
docker compose --profile bot up --build -d      # сервис bot в docker-compose.yml
docker compose logs -f bot                      # видно, кто что спрашивает
```

**Linux (systemd)** — файл `/etc/systemd/system/lead-bot.service`:

```ini
[Unit]
Description=Telegram bot (AI-native CRM)
After=network-online.target

[Service]
WorkingDirectory=/opt/ai-native-srm
EnvironmentFile=/opt/ai-native-srm/.env
ExecStart=/opt/ai-native-srm/.venv/bin/python -m channels.telegram_lead_bot
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload && sudo systemctl enable --now lead-bot
journalctl -u lead-bot -f
```

**Windows** — Планировщик задач: задание «При запуске компьютера», действие
`python -m channels.telegram_lead_bot`, рабочая папка — корень проекта, галка «Выполнять вне
зависимости от входа пользователя». Либо `nssm install lead-bot python -m channels.telegram_lead_bot`.

## Диагностика

Сначала всегда `python -m channels.telegram_lead_bot --check` (к Telegram почти не ходит:
показывает настройки, отвечает ли API, какой провайдер LLM) и, если дело в Telegram,
`python scripts\check_telegram.py` — он называет причину и печатает команды починки.

| Симптом | Причина и что делать |
|---|---|
| `Не хватает переменных: TG_LEAD_BOT_TOKEN` | токен не задан в `.env` — взять у @BotFather |
| `CRM отклонила токен бота (BOT_API_TOKEN)` | сервисные токены бота и бэкенда разошлись — привести к одному значению |
| `CRM недоступна — проверьте, запущен ли API` | не запущен uvicorn или неверный `API_URL` (в Docker — `http://api:8000`) |
| `Бот отвечает «Не понял сообщение»` | это не ошибка: вернитесь кнопкой «🏠 В меню» или напишите вопрос словами |
| Клиент не видит ответ менеджера | бот не запущен (ответ лежит в outbox) либо клиент выключил уведомления в «⚙️ Настройки»; проверить `TG_LEAD_BOT_TOKEN` и логи |
| В ленте менеджера нет запроса клиента | пустой `TG_MANAGER_CHAT_ID` — уведомления идут только в дашборд сайта |
| `TelegramConflictError: terminated by other getUpdates request` | бота опрашивает второй экземпляр или стоит webhook: `python -m channels.telegram_lead_bot --drop-webhook` и остановить лишний процесс |
| `"next start" does not work with "output: standalone"` в логах сайта | это про сайт, не про бота: подсказка Next.js, работать не мешает |
| «Карточки нет на сайте», хотя клиент заполнил профиль в боте | сайт работает на демо-данных: `CRM_BACKEND_URL` не задан или бэкенд не отвечает. Проверьте `engine` в `/api/health` сайта |
| `aiogram не установлен` | `pip install -r requirements.txt` (без aiogram API и mock-режим работают) |

## Приёмка

**1. Канал «бот → CRM → сайт»** (Telegram не нужен: скрипт шлёт те же тела, что и бот):

```powershell
python scripts\check_lead_pipeline.py --api http://localhost:8000 --site http://localhost:3000
```

Он проверяет `/api/health` → `POST /api/leads` → журнал заявок → карточку и уведомление
на сайте. Создаётся карточка «Проверка канала» — удаляется кнопкой «Сбросить демо-данные».

**2. Диалог целиком** — офлайн, без токенов:

```powershell
python -m channels.mock_telegram --demo
```

Сценарий проходит все разделы: меню → профиль (заполнение) → каталог → обращение с расчётом
скидки → спор (HOLD и уведомление менеджеру) → ответ менеджера → доставка клиенту → закрытие →
помощь, база знаний, настройки. Полезно как протокол демонстрации: видно, что именно получает
клиент и что в этот момент видит менеджер.

## Тесты

```bash
pytest tests/test_bot_flow.py -q      # 40 тестов: экраны, меню, состояния, профиль, обращения, mock-CRM
pytest tests/test_bot_api.py -q       # 14 тестов: /api/bot/* — токен, владелец, HOLD, доставка
pytest tests/test_bot_telegram.py -q  # 8 тестов: живой путь апдейта через aiogram (виджет, кнопки, доставка)
pytest tests/test_lead_bot.py -q      # 31 тест: анкета-основа, настройки, HTTP-клиент, диагностика Telegram
pytest tests/test_leads.py -q         # серверная часть: нормализация и карточка клиента
```

Логика диалога вынесена в `channels/bot_flow.py` без aiogram, поэтому проверяется обычными
тестами, а транспорт остаётся тонким. `aiogram` нужен только для реального запуска
(`pip install -r requirements.txt`) — тесты работают и без него.
