# Telegram-бот-анкета: заявка → карточка клиента

Отдельный бот от клиентского чата (`channels/telegram_bot.py`). Здесь нет ИИ и переписки:
бот задаёт пять вопросов, собирает данные о человеке и отправляет их в CRM. На сервере из
анкеты создаётся **карточка клиента**, поэтому данные сразу используются в работе сайта:
клиент виден в разделе клиентов, менеджер получает уведомление, а клиентский чат-бот находит
этого человека по `telegram_id`, когда он пишет в общий чат.

```
Telegram ──(анкета)──▶ channels/telegram_lead_bot.py ──POST /api/leads──▶ core/leads.py
                                                                              │
                                        клиент (карточка) + уведомление LEAD + событие lead_received
```

---

## Запуск

```bash
python -m channels.telegram_lead_bot --check   # настройки + доступность API, к Telegram не идём
python -m channels.telegram_lead_bot           # приём заявок (long polling)
```

Переменные окружения (см. `.env.example`):

| Переменная | Зачем |
|---|---|
| `TG_LEAD_BOT_TOKEN` | токен бота от [@BotFather](https://t.me/BotFather) — **отдельный** от клиентского бота |
| `BOT_API_TOKEN` | сервисный токен для `/api/leads` — тот же, что в `.env` бэкенда |
| `API_URL` | адрес API (по умолчанию `http://localhost:8000`) |
| `TG_MANAGER_CHAT_ID` | куда слать копию заявки менеджеру (можно несколько id через запятую) |
| `UI_URL` | адрес дашборда — попадёт ссылкой в уведомление менеджеру |

Токен бота **не** выдаётся наружу и не логируется; если `BOT_API_TOKEN` пуст, бэкенд отвечает
`503` — это сознательно, чтобы заявки не текли в CRM без защиты (Ст. 4).

## Что спрашивает бот

| Шаг | Вопрос | Обязательный |
|---|---|---|
| 1 | Как вас зовут? | да |
| 2 | Как называется ваша компания? | нет («-» — частное лицо) |
| 3 | Телефон для связи? | нет, но приводится к формату `+79991234567` |
| 4 | E-mail для документов? | нет |
| 5 | Что нужно? Коротко опишите задачу. | нет |

Правила диалога:

* пропуск — «-», «нет», «пропустить»; на обязательном вопросе пропуск отклоняется с пояснением;
* телефон не распознан → шаг повторяется, прогресс не сдвигается («Телефон не распознан. Пример: …»);
* `телефон/почта не указаны` → контактом становится сам Telegram: менеджер ответит в чате,
  заявка при этом не теряется;
* `/cancel` или «отмена» — выход; `/start` на любом шаге — анкета заново;
* перед отправкой показывается карточка «Проверьте, всё верно?» и кнопки-слова «да» / «заново»;
* API недоступен → клиент видит «Попробуйте ещё раз: «да»», ответы остаются в сессии и не теряются.

Персональные данные не нужны боту в логах: в события CRM уходит только длина запроса и факт
наличия контакта, полный текст — в карточке клиента (`core/leads.py`).

## Что происходит на сервере

`POST /api/leads` (заголовок `X-Bot-Token`) → `core/leads.py:apply_lead()`:

1. нормализация: телефон «8 (999) 123-45-67» → `+79991234567`, обрезка пробелов, проверка имени;
2. поиск существующего клиента по `telegram_id` → телефону → e-mail (первое совпадение);
3. нет клиента — создаётся карточка (`source="telegram_lead_bot"`); есть — заполняются только
   пустые поля, изменившиеся фиксируются по событию;
4. уведомление менеджеру (`type="LEAD"`) и событие `lead_received` (без ПДн в payload);
5. ответ `{ok, client_id, created, changed, name, company, notification}`.

`GET /api/leads?limit=20` — последние заявки списком (для дашборда и отладки), тоже по токену.

## Запуск как сервис (чтобы бот работал постоянно)

Long polling не требует белого IP и вебхука — боту достаточно исходящего соединения, поэтому
он спокойно живёт на ноутбуке или в контейнере за NAT.

**Docker** (рекомендуемый способ, если API уже в compose):

```bash
docker compose --profile lead up --build -d      # сервис lead-bot в docker-compose.yml
docker compose logs -f lead-bot                  # видно, кто что спрашивает
```

**Linux (systemd)** — файл `/etc/systemd/system/lead-bot.service`:

```ini
[Unit]
Description=Telegram lead bot (AI-native CRM)
After=network-online.target

[Service]
WorkingDirectory=/opt/ai-native-srm
EnvironmentFile=/opt/ai-native-srm/.env
ExecStart=/opt/ai-native-srm/.venv/bin/python -m channels.telegram_lead_bot
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload && sudo systemctl enable --now lead-bot
journalctl -u lead-bot -f
```

**Windows** — Планировщик задач: задание «При запуске компьютера», действие
`python -m channels.telegram_lead_bot`, рабочая папка — корень проекта, галка «Выполнять вне
зависимости от входа пользователя». Либо `nssm install lead-bot python -m channels.telegram_lead_bot`.

## Диагностика

Сначала всегда `python -m channels.telegram_lead_bot --check` (к Telegram не ходит, показывает
настройки и доступность API).

| Симптом | Причина и что делать |
|---|---|
| `Не хватает переменных: TG_LEAD_BOT_TOKEN` | токен не задан в `.env` — взять у @BotFather |
| `НЕ задан BOT_API_TOKEN` / `/api/leads ответит 503` | сервисный токен пуст в `.env` **бэкенда**; он же нужен боту |
| `API: НЕ отвечает — Connection refused` | не запущен uvicorn или неверный `API_URL` (в Docker — `http://api:8000`, не `localhost`) |
| `401 неверный X-Bot-Token` в логах бота | `BOT_API_TOKEN` бота и бэкенда разошлись — привести к одному значению и перезапустить оба |
| `Телефон не распознан` у клиента | это норма: шаг повторяется, пока не введут номер или «-» |
| `aiogram не установлен` | `pip install -r requirements.txt` (aiogram 3 ленивый: без него API работает) |
| «Карточки нет на сайте», хотя заявка принята | чаще всего сайт работает на демо-данных: `CRM_BACKEND_URL` не задан (или бэкенд не отвечает). Проверьте `GET /api/health` у сайта — поле `engine` должно быть `backend`; в интерфейсе об этом прямо предупреждает баннер, а приёмка `check_lead_pipeline.py` останавливается с этой подсказкой |
| Ответы не идут менеджеру в Telegram | пустой `TG_MANAGER_CHAT_ID` или неверный id (узнать у @userinfobot); в логах — `Не смог уведомить менеджера` |
| Бот отвечает «Попробуйте ещё раз: «да»» | API был недоступен в момент отправки; ответы сохранены в сессии, повторная «да» досылает анкету |

Проверить, что заявки доходят, можно и без Telegram — отправить анкету напрямую:

```bash
curl -X POST http://localhost:8000/api/leads -H "X-Bot-Token: $BOT_API_TOKEN" \
     -H "Content-Type: application/json" \
     -d '{"name":"Тест Тестов","phone":"8 999 000-11-22","request":"проверка ручки"}'
```

## Приёмка: проверить весь канал одной командой

Телеграм для этого не нужен: скрипт отправляет анкету прямо в API — тем же телом, что и бот, —
и проверяет каждый участок пути.

```powershell
python scripts\check_lead_pipeline.py --api http://localhost:8000 --site http://localhost:3000
```

Что проверяется и что печатает скрипт:

| Шаг | Проверка | Если порвалось |
|---|---|---|
| 1 | `GET /api/health` — API жив | покажет команду запуска бэкенда |
| 2 | `POST /api/leads` — ручка принимает анкету | 401 → токены разошлись, 503 → `BOT_API_TOKEN` не задан |
| 3 | `GET /api/leads` — заявка в журнале | подскажет смотреть логи API |
| 4 | сайт: карточка в клиентах и уведомление «Заявка из бота» | подскажет проверить `CRM_BACKEND_URL` и файл БД |

Скрипт создаёт в базе карточку «Проверка канала» — это нормально, удаляется кнопкой
«Сбросить демо-данные» в сайдбаре. Работает без зависимостей проекта: `BOT_API_TOKEN` берёт
из `.env`, логин/пароль сайта — из ключей `--login`/`--password`.

## Тесты

```bash
pytest tests/test_lead_bot.py -q     # 23 теста: анкета, пропуски, ошибки, конфиг, HTTP-вызов
pytest tests/test_leads.py -q        # серверная часть: нормализация и карточка клиента
```

Логика опроса вынесена в `channels/lead_flow.py` без aiogram — поэтому проверяется обычными
тестами, а обвязка бота остаётся тонкой. `aiogram` нужен только для реального запуска
(`pip install -r requirements.txt`), в остальных случаях тесты работают без него.
